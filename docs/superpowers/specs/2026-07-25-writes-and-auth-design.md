## 1. Goal

Replace the five "Read-only deployment" stubs with real, persisted actions, and replace
the fake login with real Catalyst Authentication and server-enforced role-based scope.

This directly serves Challenge 2's governance requirement and the framework item
*"Secure Role-Based Access & Governance — role-based access for investigators, analysts,
supervisors and policymakers; secure handling of sensitive data with audit logs and

| Control | File |
|---|---|
| Add Note | `client/src/routes/CaseDetails.tsx:149` |
| Update Status | `client/src/routes/CaseDetails.tsx:163` |

## 2. The constraint that determines the architecture

The frontend is served from `ksp-crime-intelligence-*.development.catalystserverless.in/app/`.
The read API is a separate origin: `kspapi-*.development.catalystappsail.in`.

Catalyst's Web SDK loads from the same-origin path `/__catalyst/sdk/init.js` and maintains
the session in a **cookie scoped to the Web Client Hosting domain**. That cookie is never
sent to the AppSail domain. Any design that POSTs from the browser directly to the existing
AppSail API therefore arrives **anonymous**, and `catalyst.initialize(req)` cannot resolve a user.

**Consequence:** the authenticated write API must be served from the *same origin* as the
frontend. Catalyst Advanced I/O Functions are served at `/server/<function_name>/…` on that
origin. So writes live in a Function, not in AppSail.

## 3. Architecture

Strictly additive. **No file in `catalyst-app/appsail/` changes, and AppSail is not redeployed.**

```
Browser (catalystserverless.in/app/)
  ├── GET  reads ────────────────► AppSail  kspapi   (unchanged, SQLite via sql.js)
  └── GET/POST/PUT writes+session ► Function kspwrite (same origin, cookie flows)
                                       ├── Catalyst Authentication  (identity)
                                       ├── Catalyst Data Store      (persistence)
                                       └── org.json / case-station.json /
                                          crime-case.json / featured.json (bundled)
```

Mandated services used: Authentication, Data Store, Serverless Functions, Web Client
Hosting, AppSail.

### Why the bundled JSON files

`kspwrite` must answer these on every mutating request **without trusting the client**,
and without a database round-trip. All four are generated by `server/export-write-data.mjs`
from `data/generated/ksp.db` and committed:

| File | Answers | Size |
|---|---|---|
| `org.json` | Which units does this officer command? (44 units, 5 types, 10 ranks) | ~3 KB |
| `case-station.json` | Which station does case N belong to? (5,200 cases) | ~50 KB |
| `crime-case.json` | Which case is `CrimeNo` X? (5,200) | ~60 KB |
| `featured.json` | Which case does the Case Details page show? | tiny |

`crime-case.json` keys on `CrimeNo`, not `CaseNo`: **`CaseNo` is not unique in the
generated data** — 5,200 cases share only 261 distinct `CaseNo` values, while `CrimeNo` is
one per case. `featured.json` mirrors the read API's `/api/cases/featured` ordering, so the
write layer can address the case the page is showing without modifying AppSail.

These files only *identify* a case. The station always comes from `case-station.json`, so a
caller naming an arbitrary case id still cannot act outside their own command scope.

## 4. Identity and scope

**Credentials are owned entirely by Catalyst Authentication.** We never store or verify a
password. Sign-in uses embedded authentication: `catalyst.auth.signIn("login", config)`
injects Catalyst's iframe form into the existing Login page, styled via `css_url` to match
`client/src/styles/tokens.css`. The page's branding, imagery and feature cards are retained;
only the credential fields become the iframe.

**Authorization is ours**, and derives from the org-chart spine already described in
`architecture.md` §6:

1. `catalyst.initialize(context)` → authenticated email.
2. Email → `AppUser` row → `UnitID`, `RankID`, `Role`.
3. `UnitID` → descendant set over the `Unit.ParentUnit` tree → **visible/actionable scope**.

The client never supplies identity, unit or scope. It is read server-side from the session
on every request. A tampered request body cannot widen scope.

Scope ladder in the seeded data:

| Rank | Unit | Sees | On the featured case |
|---|---|---|---|
| Sub-Inspector (RankID 8) | Indiranagar PS (UnitID 22) | 1 station | **allowed** |
| ASP (RankID 5) | Bengaluru South Division (UnitID 3) | its stations | **refused** |
| DGP / SCRB (RankID 1) | Karnataka State Police (UnitID 1) | all 44 units | **allowed** |

The featured case (CaseMasterID 1733) sits in **Indiranagar PS, Bengaluru East Division**,
which is what makes this set worth demonstrating: the ASP *outranks* the SI and is still
refused, because authority follows command position, not rank. `scope.test.js` asserts
exactly this property.

The existing hardcoded officer — *R. Sharath Kumar, IPS, ASP, Bengaluru South Division* —
becomes the ASP account, so the current demo identity is preserved.

## 6. API surface — function `kspwrite`

Base path `/server/kspwrite`. All responses JSON. Unauthenticated → `401`.
Out-of-scope → `403` **and an `AuditLog` row with `Outcome='deny'`**.

| Method | Path | Purpose |
|---|---|---|
| GET | `/session` | Current user, scope, unit breadcrumb; `{authenticated:false}` when signed out |
| GET | `/cases/:id/overlay` | `{ notes[], statusChange, effectiveStatusId }` for merging into the read model |
| POST | `/cases/:id/notes` | Body `{text}` → creates `CaseNote` |
| POST | `/cases/:id/status` | Body `{toStatusId, reason}` → creates `CaseStatusChange` |
| POST | `/cases/:id/close` | Body `{reason}` → `CaseStatusChange` to status 4 |
| GET | `/profile` | Merged `AppUser` + `UserProfile` |
| PUT | `/profile` | Body `{displayName, phone, preferredLanguage}` |
| GET | `/audit?limit=50` | Recent audit entries within the caller's scope |

Every mutating handler follows one path: resolve session → resolve `AppUser` → look up the
case's station in `case-station.json` → test membership in the caller's descendant set →
write the row → write the `AuditLog` row. Denials short-circuit after the membership test
but **still write the audit row**.

**Change Password is not implemented here.** It is delegated to Catalyst's own
password-reset flow (the Web SDK's forgot-password / Catalyst-hosted reset page; exact
method to be confirmed against the console during implementation), so no credential
handling code exists in this codebase.

## 7. Read overlay

Reads remain authoritative from SQLite via AppSail. Writes are layered on top client-side:

- Effective status = latest `CaseStatusChange.ToStatusID` if one exists, else the base
  `CaseStatusMaster` status from AppSail.
- Notes = `CaseNote` rows, newest first, rendered in the Case Details timeline.

`CaseDetails.tsx` fetches base case data from AppSail and the overlay from `kspwrite`,
then merges. AppSail is not aware the overlay exists.

## 8. Frontend changes

- `client/src/api.ts` — add `apiPost` / `apiPut` and a `WRITE_BASE` (`/server/kspwrite`),
  with `credentials: "include"`. Existing `apiGet` is untouched.
- `client/src/auth.tsx` — new. Loads the Web SDK, exposes `useSession()`, sign-in, sign-out.
- `client/src/routes/Login.tsx` — replace the mock form with the embedded auth div; keep the
  surrounding layout. Redirect to `/` when already authenticated.
- `client/src/routes/CaseDetails.tsx` — wire the three actions to real endpoints; add a note
  composer and render notes in the timeline tab.
- `client/src/routes/Settings.tsx` — wire Edit Profile; point Change Password at Catalyst's flow.
- `client/src/components/TopBar.tsx` — prefer the real officer and scope from `/session`
  when authenticated, falling back to the existing `/api/meta` officer when signed out;
  add sign-out. The `/api/meta` call itself is unchanged.
- `client/src/routes/AuditTrail.tsx` — new view listing recent `AuditLog` entries, allowed
  and refused, added to the sidebar's secondary nav.

## 9. Degradation and error handling

Signed out, or if `kspwrite` is unreachable, every write control keeps today's toast
behaviour. **The current demo cannot regress.**

| Condition | Behaviour |
|---|---|
| 401 | Toast "Session expired", redirect to `/login` |
| 403 | Toast "Outside your command scope — attempt recorded"; the denial is visible in Audit |
| 5xx / network | Toast with retry; optimistic UI rolls back |
| Note > 2000 chars | Client-side validation before submit |

Writes are optimistic with rollback on failure.

## 10. Testing

- **Unit (`node:test`)** — `scope.js` is pure: given `org.json`, assert an SI's descendant
  set is exactly one station, an ASP's is their division's stations, DGP's is all 44. Assert
  `canActOn()` denies a Jayanagar SI acting on a Bengaluru North case, and that a
  South-division ASP is refused on the East-division featured case.
- **Integration** — run the function locally with `catalyst serve`; exercise each endpoint
  signed-out (401), in-scope (201), out-of-scope (403 + audit row).
- **Manual deploy check** — sign in as each of the three demo officers and confirm the scope
  label, an allowed write, and a denied write.

## 11. Demo narrative

1. Sign in as **SI, Indiranagar PS** — scope shows one station.
2. Add a note to the featured case → persists, appears in the case-file timeline.
3. Sign out, sign in as **ASP, Bengaluru South Division** — a higher rank. The case page
   shows the out-of-scope banner; attempting a status change is refused.
4. Sign in as **SCRB (DGP)** — state-wide scope; the same action succeeds.
5. Open Audit Trail → the allowed actions *and the refused attempt* are listed with actor,
   unit, timestamp and outcome.

Step 5 is the point: it demonstrates the control is enforced, not decorative.

## 12. Risks

| Risk | Severity | Mitigation |
|---|---|---|
| Console setup (tables, auth) not finished in time | High | Checklist delivered first so it proceeds in parallel with coding |
| Embedded auth iframe styling fights the design | Medium | `css_url` against existing tokens; acceptable unstyled fallback |
| Function deploy fails late | High | Deploy a `/session` stub first to prove the path, then fill in |
| Cookie still not reaching the function | Medium | Same-origin by construction; verified by the `/session` stub before further work |
| Data Store dev-tier row cap | Low | Demo volume is tens of rows |

## 13. Out of scope

Password change implementation, user self-registration, note editing/deletion, attachments,
migrating any read path to Data Store, and changes to the AppSail service.
